# PM：產品與製作管理文件

版本：0.1｜專案：手機優先的單人 Roguelite 自動跑酷射擊遊戲｜關聯：[遊戲規格](../Arrow-a-Row-開發規格書.md)、[UI 規格](../Arrow-a-Row-畫面流程與UI規格.md)、[技術規範](../Arrow-a-Row-技術設計與程式規範.md)

## 1. PM 的使命與決策權

PM 對「做什麼、何時做、以何種可驗收品質交付」負責；不直接決定傷害公式、模型拓撲或程式實作。PM 擁有範圍、優先級、版本切割與 Go/No-Go 決策權，並維護單一需求真相來源。

產品目標：在 iOS／Android 上提供可單手遊玩的 4–8 分鐘 Roguelite Run；玩家自動前進與射擊，只用左右拖曳選路、躲彈與組 Build；核心離線可玩。

## 2. 成功指標與產品護欄

| 層面 | MVP 成功標準 | 量測來源 |
| --- | --- | --- |
| 可玩性 | 5 名新玩家中至少 4 名在 10 秒內完成首次移動與過門 | 可用性測試錄影。 |
| 核心循環 | 首局到達第一 Boss 60–75%；擊敗率 30–45% | 30 位測試者／bot run。 |
| 技術品質 | Standard 裝置 60 FPS P95 <16.7ms；P0 crash=0 | 真機 profiling、QA。 |
| 恢復性 | 任意 Run 切後台／OS 回收後可從 checkpoint 恢復 | 手機相容性測試。 |
| 內容 | 3 章、3 Boss、24 一般能力、12 Boss 獎勵可完整跑通 | Content checklist。 |

產品護欄：不做強制廣告、付費戰鬥數值或連網必需；不複製參考作品的 IP；不為「看起來完整」而跳過存檔、前後台與低階機驗收。

## 3. 範圍定義

### MVP 必做

| Epic | 可交付結果 | Owner |
| --- | --- | --- |
| Core Run | 直式單手拖曳、自動射擊、岔路、敵人、死亡／重開 | 工程＋遊戲設計。 |
| Roguelite | 24 能力、三選一、重擲、3 種 Build 可通關 | 遊戲設計＋工程。 |
| Meta | 金幣、6 永久升級、解鎖、商店、存檔 | 工程＋UI。 |
| Mobile UX | 主選單、HUD、暫停、結算、safe area、前後台 | UI＋工程＋QA。 |
| Content | 3 主題、4 普通敵人、3 Boss、原創世界觀與音效 | 世界觀、美術、建模、音效。 |
| Quality | Android／iOS 目標裝置、離線、30／60 FPS、測試與 CI | 工程＋QA。 |

### 明確不納入 MVP

多人、排行榜、帳號系統、雲端同步、推播、廣告、內購、LiveOps 活動、無盡模式以外的新遊戲模式、故事動畫、裝備背包。任何需求要加入 MVP，必須移除等量範圍或取得 PM 的版本延後核准。

## 4. 里程碑與出入口

| 里程碑 | 目標 | 進入條件 | 離開（Gate） |
| --- | --- | --- | --- |
| M0 規劃 | 可開工的產品基線 | 三份基礎規格已核准 | 所有 Epic 有 owner、風險、驗收。 |
| M1 灰盒核心 | 30 秒可玩循環 | Input、Run state、灰盒內容 | 移動／射擊／門／死亡 P0 全過。 |
| M2 垂直切片 | 一章完整品質樣本 | M1 通過 | 一章、Boss、獎勵、商店、前後台、效能達標。 |
| M3 Feature Complete | 所有系統已接入 | M2 通過 | MVP 功能完成、內容可替換、無新增大型 Epic。 |
| M4 Content Complete | 遊戲可從頭到尾遊玩 | M3 通過 | 3 章與所有 MVP 內容完成、文案鎖定。 |
| M5 RC | 發版候選 | M4 通過 | P0=0、P1 有 owner／修復日期、真機矩陣通過。 |
| Release | 分階段發佈 | 商店／隱私／簽署完成 | 監控 crash、ANR、checkpoint 失敗後擴量。 |

## 5. Backlog 管理

每張工作卡必含：`ID`、問題／玩家價值、範圍、非範圍、驗收條件、設計／技術連結、owner、依賴、風險、測試案例、分析事件、估點、版本。

優先序使用 RICE：`Reach × Impact × Confidence / Effort`，但 P0 品質、平台合規與資料安全不參與取捨，永遠優先。需求狀態：`Draft → Ready → In Progress → In Review → QA Ready → Verified → Done`；沒有驗收條件的卡不可進 Ready。

## 6. 節奏與會議

| 節奏 | 參與者 | 產出 |
| --- | --- | --- |
| 每日 15 分鐘 | 全員 | 阻塞、當日目標、跨職能依賴。 |
| 每週規劃 | PM、各 owner | 下一週承諾、範圍差異、風險。 |
| 每週 Playtest | PM、設計、UI、工程、QA | 錄影、觀察、3 項可執行改善。 |
| 每兩週 Review | 全員／利害關係人 | 可玩的 build 與已驗收結果，不展示 mock。 |
| 每里程碑 Gate | PM、Tech Lead、QA Lead | Go／Hold／降範圍決議與紀錄。 |

## 7. 需求變更控制

1. 提出者描述玩家問題與預期效益。
2. PM 估算範圍、時程、風險、需移除的項目；各 owner 補技術／美術成本。
3. 若影響已鎖定內容、存檔、經濟或平台合規，建立 RFC，至少等待一個 review cycle。
4. PM 記錄 `Accepted / Deferred / Rejected` 與理由，更新基線文件與 backlog。
5. 任何口頭決定 24 小時內寫入決策紀錄（ADR/Decision log）。

## 8. 風險台帳

| 風險 | 預警訊號 | 緩解 | Owner |
| --- | --- | --- | --- |
| 內容產量過大 | M2 後一章仍未完成 | 先鎖 3 章、重用系統、削減變體 | PM＋美術 lead。 |
| 手機效能不足 | 中階機戰鬥 P95 超標 | 垂直切片即 profile；彈體、VFX、陰影分級 | Tech Lead。 |
| 壞 RNG | playtest 頻繁無力死亡 | 保底、權重、重擲、seed replay | 遊戲設計。 |
| 存檔遺失 | 前後台測試不一致 | checkpoint 雙檔、migration、故障注入 | 工程＋QA。 |
| UI 誤觸 | 選卡／放棄 Run 誤按 | 觸控熱區、二次確認、錄影測試 | UI＋QA。 |
| IP 相似 | 名稱／視覺接近參考 | 原創世界觀、資產清單、發行前審查 | PM。 |

## 9. PM 驗收包

每個 milestone 的 PM 交付物：已核准 scope、變更紀錄、可玩 build 連結、驗收結果、已知問題列表、風險台帳、內容完成表、下階段計畫。PM 僅在 QA 證據存在時標記完成；「已實作」不等於「已驗收」。
